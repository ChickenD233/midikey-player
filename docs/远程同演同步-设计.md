# 远程同演同步：设计文档

目标：几个人绑定到一个房间，每人负责一个或几个声部，锁定各自的移调，然后一同演奏同一首 MIDI。

界面位置：设置窗口新增「实验功能」页，排在「赞助」页右面。

传输方式：公共 MQTT 代理，走 WebSocket。不写服务器，不租服务器。

状态：设计稿第二版，等待确认后开工。

---

## 一、先定一件不能做的事

网络传按键做不到毫秒级同步。原因有两条。

1. 目标程序读一次按键的窗口只有 1 到 2 帧，约 16 到 33 ms。
2. 公网往返延迟 30 到 100 ms，且抖动。

所以本方案不传按键。本方案传的只有三样东西：谁弹哪个声部、移调几度、从什么时候开始。

按键由每台机器本地发出，与本地播放走同一条代码路径。网络抖动不进游戏。

## 二、参考项目：Bili-SyncPlay

参考地址：https://github.com/sky1wu/Bili-SyncPlay

它是一个浏览器扩展加一台 WebSocket 服务器，用来同步 B 站视频播放。

### 2.1 连接方式

所有客户端主动连服务器。服务器有公网地址。

```
扩展 A ──┐
扩展 B ──┼──> WebSocket 服务器
扩展 C ──┘
```

NAT 只拦入站连接，不拦出站连接。因此不需要公网 IP，不需要端口转发，不需要打洞。

### 2.2 它明确不信任时钟比较

`extension/src/background/clock-sync.ts` 的注释：

> 位置从本机单调时钟锚点推算，正因为没有滤波器能让双钟比较变得可信。

它算出的 `clockOffsetMs` 只用来显示诊断，不进播放。

它记录了一个实测：同一台机器上，浏览器与 WSL 里的服务端，两个时钟在一分钟内偏移从 -893 ms 漂到 +1264 ms，而往返只有 1 ms。

### 2.3 它怎么算位置

只加本机测到的流逝量。不拿对端时间戳减本机时间戳。

```
目标位置 = 快照里的位置 + 本机已流逝时间 × 倍速
```

### 2.4 它的 RTT 过滤

- 每 15 秒发一次 ping。
- 保留最近 8 个样本，超过 150 秒的作废。
- 只让 RTT 小于等于最快值加 20 ms 的样本参与。
- 取这些样本的中位数。
- 变化小于 120 ms 就不更新。

## 三、MQTT 替代自建服务器

第二条已经写了 Bili-SyncPlay 的做法：所有人主动连一台公网服务器。

那台服务器只干三件事：转发消息、发房间码、存房间快照。

MQTT 代理天生就会这三件事，而且是免费的。所以不写服务器。

### 3.1 MQTT 是什么

MQTT 是物联网用的消息协议。模型是发布 / 订阅：

```
客户端 A ──发布──┐
客户端 B ──发布──┼──> MQTT 代理 ──推送──> 所有订阅该主题的人
客户端 C ──订阅──┘
```

代理负责把一条消息发给同主题的所有人。这正是我们需要的。

MQTT 用一个概念解决迟到者问题：**保留消息**。代理会记住每个主题的最后一条消息，新人一订阅就立刻收到。我们把它用来传房间快照。

### 3.2 可用的公共代理

| 家 | 明文 WebSocket | 加密 WebSocket | 路径 |
|---|---|---|---|
| EMQX | `ws://broker.emqx.io:8083/mqtt` | `wss://broker.emqx.io:8084/mqtt` | `/mqtt` |
| HiveMQ | `ws://broker.hivemq.com:8000/mqtt` | `wss://broker.hivemq.com:8884/mqtt` | `/mqtt` |

EMQX 的公开代理是地理分布式集群，国内延迟通常比 HiveMQ 低。默认用 EMQX。

**连接时必须声明 `mqtt` 子协议。** 不声明时 EMQX 直接回 HTTP 400，报错是
"The server returned status code '400' when status code '101' was expected"，
看不出原因。HiveMQ 两种都收，所以这条只在 EMQX 上会踩到。

来源：https://www.emqx.com/en/mqtt/public-mqtt5-broker 与 http://www.mqtt-dashboard.com/

.NET 8 自带 `System.Net.WebSockets`，不需要新增第三方依赖。

### 3.3 免费额度

公共代理完全免费，不用注册。属于测试用服务，没有服务承诺。

要更稳定，可以用注册后的免费层：

| 家 | 免费层 | 会话分钟 | 带鉴权 |
|---|---|---|---|
| EMQX Cloud Serverless | 有 | 100 万 / 月 | 是 |
| HiveMQ Cloud | 有 | 有上限 | 是 |

三个人每月用 10 小时，约 1800 会话分钟。免费层够用。

第一版只用公共代理。地址写进邀请串，用户不用填。

### 3.4 四个代价

1. **消息明文。** 公共代理不加密，也不鉴权。任何人都能订阅任何主题。
2. **可以冒充主机。** 别人知道主题名，就能发假的开演、暂停、跳转。
3. **服务不保证活着。** 它是测试服务，可能限速、清空保留消息、甚至关停。
4. **QoS 1 会重复投递。** "至少一次"语义意味着同一条开演消息可能到两次。重复会让播放头跳一下。

### 3.5 四条必要的防护

1. **主题名随机化。** 房间码用 128 位随机值。猜不到就订阅不到。
2. **消息序号去重。** 每条控制消息带递增序号。序号已处理过就丢弃。这条同时解决代价 4。
3. **加消息签名。** 建房时生成一个 128 位密钥，放进邀请串。每条消息带 HMAC-SHA256 前 16 字节。签名不对就丢弃。这条解决代价 2。
4. **成员名单校验。** 只接受成员表里的成员发来的消息。

### 3.6 延迟现实

公共代理的服务器在境外。国内实测延迟可能到 150 到 250 ms。

这不影响我们的模型。因为开演用的是"从现在起再等多久"，不是绝对时刻。延迟大只让等待更长。

影响精度的是**抖动**，不是延迟本身。开演精度约等于抖动的一半。抖动 ±50 ms 时，精度约 ±25 ms。游戏判定吃得下。

页面上显示实测 RTT 与抖动，让用户自己判断。

## 四、我们采用的做法

### 4.1 比它更省事的一点

它必须在本机单调时钟上加锚点，因为浏览器不信任两台机器的钟。

我们只有一个进程，`Stopwatch.GetTimestamp()` 和 `Environment.TickCount64` 就是单调时钟。

**关键决定：主机传的是"从你收到这一刻起再等多久"，不是绝对时刻。**

流程：

1. 主机广播 `Start { DelayMs = 800 }`。
2. 每台客户端收到就设 `StartAt = Stopwatch.GetTimestamp() + 800ms`。
3. 到点开演。

两台机器的墙钟差直接消失。不需要 NTP，不需要时钟滤波。

### 4.2 时钟估计的唯一用途

只用来让主机算开演余量。

1. 每台报一次 RTT。
2. 主机取最大 RTT。
3. 余量 = 最大 RTT ÷ 2 + 150 ms。

RTT 过滤照抄 2.4 节的规则。

### 4.3 已知代价

同一条控制消息到达各人的时刻相差半个 RTT 加半个抖动。

- 同一个 WiFi：约 1 ms。可忽略。
- 走国内公共代理：约 30 到 80 ms。
- 走境外公共代理：约 75 到 125 ms。

慢速校正会把持续偏差压回 ±30 ms 以内。

因此**推荐用 EMQX 的公开代理**，它的集群是地理分布的。

## 五、系统结构

```
        ┌────────────────────────────────────┐
        │  MQTT 代理（公共，只转发，不写代码）  │
        │  主题 mkp/<房间码>/ctl  控制消息      │
        │  主题 mkp/<房间码>/state 保留快照     │
        └────────────────────────────────────┘
             ▲          ▲          ▲
             │          │          │
        ┌────┴───┐ ┌────┴───┐ ┌────┴───┐
        │ 客户端 │ │ 客户端 │ │ 客户端 │
        │ 声部 1 │ │ 声部 2 │ │ 声部 3 │
        └────────┘ └────────┘ └────────┘
```

职责划分：

| 谁 | 做什么 |
|---|---|
| MQTT 代理 | 转发消息、用保留消息存一份房间快照 |
| 主机（建房者） | 权威。定声部、定移调、定开演时刻 |
| 成员 | 本地演奏。上报进度差。可改自己的声部与移调 |

代理不做的事：

1. 不传 MIDI 文件。
2. 不传按键。
3. 不参与时间计算。
4. 不做鉴权。鉴权由我们在消息里自己做（见 5.5 节）。

主机掉线时，其他人自动暂停并等待。房间码不变，主机回来就接着用。

## 六、传输方式

### 6.1 协议与实现

用 MQTT 3.1.1 over WebSocket。

实现方式：手写 MQTT 报文编解码，约 350 行。理由：

1. .NET 8 自带 `System.Net.WebSockets`，不再需要网络库。
2. 第三方 MQTT 库（MQTTnet）会增大单文件 exe，并要加裁剪根程序集。
3. 我们只用五个报文类型，手写比引依赖更可控。

用到的报文：

| 报文 | 值 | 用途 |
|---|---|---|
| CONNECT | 1 | 连接，带保活 60 秒 |
| CONNACK | 2 | 确认连接 |
| PUBLISH | 3 | 收发消息，QoS 1 |
| PUBACK | 4 | QoS 1 确认 |
| SUBSCRIBE | 8 | 订阅房间的两个主题 |
| SUBACK | 9 | 订阅确认 |
| PINGREQ | 12 | 保活 |
| PINGRESP | 13 | 保活回应 |
| DISCONNECT | 14 | 断开 |

其他报文不发，收到就忽略。这样代码量很小。

### 6.2 主题设计

房间码是 128 位随机值，写成 32 位小写十六进制。

```
mkp/<房间码>/ctl      控制消息。QoS 1，不保留
mkp/<房间码>/state    房间快照。QoS 1，保留
```

为什么分成两个主题：

1. 迟到者订阅后，代理立刻把 `state` 上的保留消息推给他。
2. `ctl` 不保留，避免新人对旧的控制消息做反应。

保留消息是代理端的一个小存储。它只存最后一条，不占空间。

### 6.3 消息格式

WebSocket 二进制帧，内容是 UTF-8 的 JSON。

字段用短名，减少带宽：

```json
{ "t": "start", "seq": 12, "delayMs": 1200, "pos": 0 }
```

### 6.4 消息类型

| 类型 `t` | 谁发 | 载荷 | 说明 |
|---|---|---|---|
| `join` | 成员 | 成员 ID、名字、RTT、抖动 | 加入房间 |
| `leave` | 成员 | 成员 ID | 退出 |
| `roster` | 主机 | 成员表 | 有人进出时发 |
| `assign` | 主机 | 成员 ID、声部列表、移调 | 锁定该成员的声部与移调 |
| `fp` | 主机 | 曲目指纹、声部名表、总时长 | 开演前校验用 |
| `ready` | 成员 | 成员 ID、是否就绪、指纹是否一致 | 就绪确认 |
| `arm` | 主机 | 倒计时秒数 | 进入就绪确认 |
| `start` | 主机 | `delayMs`、起始位置 | 定时开演 |
| `pause` | 主机 | 当前位置 | 暂停并记录位置 |
| `resume` | 主机 | `delayMs`、当前位置 | 从位置继续 |
| `seek` | 主机 | 位置 | 跳转 |
| `rate` | 主机 | 速度 | 变速 |
| `stop` | 主机 | 无 | 结束本轮 |
| `probe` | 成员 | `t0`、序号 | 测 RTT |
| `echo` | 主机 | `t0`、序号 | 回 RTT |
| `drift` | 成员 | 成员 ID、进度差、当前速度 | 每 2 秒一次 |

`ping` / `pong` 已删除。那原本是服务器的心跳，现在由 MQTT 的 PINGREQ 承担。

RTT 改为成员与主机之间测：成员发 `probe`，主机回 `echo`。这样量到的正是开演要用的那段延迟。

### 6.5 消息鉴权

代理不做鉴权，所以自己做。

1. 建房时生成 128 位密钥，放进邀请串。
2. 每条消息加两个字段：`seq`（递增序号）与 `mac`。
3. `mac` = HMAC-SHA256(密钥, 除 `mac` 外的整个 JSON 规范化字节) 的前 16 字节，写成 32 位十六进制。
4. 收到消息先验 `mac`。不对就丢弃，并记一次日志。
5. 再查 `seq` 是否已处理过。已处理过就丢弃。这条同时解决 QoS 1 的重复投递。
6. 最后查发送者是否在成员表里。不在就丢弃。

### 6.6 曲目一致性

开演前必须校验曲目指纹。

1. 指纹算法：MIDI 文件字节的 SHA-256，取前 16 位十六进制。
2. 主机广播 `fp`。
3. 任一成员的指纹不一致，该成员在自己界面上看到原因，且不进入开演。
4. 声部名表也一起校验。声部数量或顺序不一致同样拒绝。
5. 总时长相差超过 0.1 秒也拒绝。时长不同说明文件不同。

### 6.7 邀请串

用户唯一要复制的东西。服务器地址不再单独填，全部打包进邀请串。

格式：

```
mkp://<代理主机>:<端口>/mqtt|<房间码>|<密钥>
```

实例：

```
mkp://broker.emqx.io:8084/mqtt|a7f39c2e1b4d60854e0f1a2b3c4d5e6f|9f8e7d6c5b4a39281706f5e4d3c2b1a0
```

拆解：

| 段 | 例子 | 说明 |
|---|---|---|
| 代理地址 | `broker.emqx.io:8084/mqtt` | 默认值。用户不填 |
| 房间码 | 32 位十六进制 | 128 位随机。猜不到 |
| 密钥 | 32 位十六进制 | 128 位随机。用来算 HMAC |

界面上三件事：

1. 建房后显示邀请串，旁边一个「复制」按钮。
2. 加入时粘贴邀请串，点「加入」。
3. 一个折叠的「高级」区，可以改代理地址。默认收起。

加入方粘贴后立刻能算出两个主题名，直接订阅。

## 七、时间模型

### 7.1 单调锚点

每个客户端维护一个锚点：

```
Anchor = (PositionSec, AtTick)
```

含义：在 `AtTick` 这个本机单调时刻，曲子位置是 `PositionSec`。

当前应有的位置：

```
现在位置 = PositionSec + (NowTick - AtTick) 换算成秒 × Speed
```

### 7.2 收到控制消息时

| 消息 | 动作 |
|---|---|
| `start` | 等 `delayMs`，然后从起始位置开演，设锚点 |
| `pause` | 停下，记下当前位置，锚点作废 |
| `resume` | 等 `delayMs`，从消息里的位置继续，设新锚点 |
| `seek` | 停下，跳到位置，设新锚点 |
| `rate` | 改速度，用当前位置重设锚点 |
| `stop` | 停止，清锚点 |

### 7.3 漂移校正

每 2 秒客户端上报一次进度差：

```
偏差 = 本机位置 - 目标位置
```

主机汇总。校正规则：

| 偏差 | 动作 |
|---|---|
| 小于 30 ms | 不动 |
| 30 到 120 ms | 微调速度，例如 ±2%，持续 5 秒 |
| 大于 120 ms | 跳转到目标位置，重设锚点 |

微调速度不改变用户看到的速度数字。它作用在内部积分上。

## 八、声部分配

### 8.1 自动分配

主机点「一键分配」。

1. 读取曲目的全部声部，按优先级排序。
2. 按在场人数轮流发牌。发牌顺序：声部按音量或音轨序号排。
3. 每人拿到相等数量的声部。
4. 发牌结果填进成员表。

鼓轨单独处理：默认整个鼓轨发给一个人，不拆开。

### 8.2 手动覆盖

每个人可以自己改自己的声部。

1. 主持人分配之后，成员可在自己界面勾掉或加回声部。
2. 已被别人占用的声部显示为占用状态，勾不上。
3. 要抢占用中的声部，需要主机在界面上点「移交」。
4. 冲突时主机拒绝改动，界面上显示具体原因。

### 8.3 移调锁定

每个人有自己的移调，范围同样是 ±24 半音。

1. 分配时默认 0。
2. 成员可以自己改，改完上报主机。
3. 开演后锁定，不能再改。

移调作用在声部合并之后、按键映射之前。与现在的 `NoteMapper.Map(raw, transpose, null)` 调用一致。

## 十一、界面

### 11.1 「实验功能」页

页面只有一张卡：远程同演。

未连接时：

1. 成员名输入框。默认取上次用过的名字。
2. 「创建房间」按钮。
3. 邀请串输入框加「加入」按钮。
4. 一行折叠的「高级」区：可以改代理地址。默认收起，内容为 `broker.emqx.io:8084/mqtt`。
5. 一行折叠说明：「连不上怎么办」。里面写清三件事：代理可能在维护、换个代理试、检查本机网络。

已连接时：

1. 第一行：成员数、连接状态、RTT、抖动。
2. 邀请串显示加「复制邀请串」按钮。主机才有。

| 情况 | 处理 |
|---|---|
| 连不上代理 | 指数退避重连，最多 10 次，界面显示第几次 |

| 目标窗口失焦 | 沿用现有焦点守卫，本地暂停。上报主机，其他人照常 |

## 十六、为什么不用自建服务器

自建服务器是最稳的方案。它需要你租一台机器，约 20 到 40 元每月，并做 TLS。

第一版不做。理由：

1. 你要先有服务器，才能验证功能是否值得。
2. 传输层已抽成接口，以后加自建实现约半天。
3. 公共代理零成本，能立刻和朋友试。

将来要加，只需新增一个实现类，界面不变。

### 19.0.1 声部编号为什么全场一致

声部序号来自"勾选顺序"（`ActiveRows` 的顺序）。各人自己勾，勾的顺序就可能不同，
于是同一个序号在不同机器上指向不同的轨。

所以建房或加入时，程序自动把所有候选轨按**文件里的列表顺序**勾进合奏。
编号从此只由文件决定，全场一致。

### 19.2 真机联调挖出来的六个坑

这六个都不是猜出来的，是连上真实代理跑出来的。每一个都写进了代码注释，并用自检用例钉住。

**一、EMQX 要求 WebSocket 子协议 `mqtt`。** 不声明就回 HTTP 400，
报错是 "The server returned status code '400' when status code '101' was expected"，
完全看不出原因。HiveMQ 两种都收，所以这条只在 EMQX 上会踩到。

**二、签名占位符长度必须与规范串一致。** `SerializeWithoutMac` 写的是 `"Mac":""`，
校验时却换成 32 个 0，长度不同 → 算出的签名必然对不上。报错只说"验签失败"。
现在改成清成空串，与规范串完全一致。

**三、`Join` 必须在成员表校验之前放行。** 新人第一次说话时还不在成员表里，
先查成员表就会丢掉它自己的入场申请。症状很怪：双方都连上了、都能收到保留快照，
但成员表永远只有主机一个人。现在是主机收到 `Join` 就先登记，不查成员表。

**四、开演等待要减掉消息在路上的时间。** 原设计里 `DelayMs` 的口径是
"收到之后再等这么久"，于是每个成员比主机晚整整一个传输时间开演（实测 219 毫秒），
而且各人延迟不同 → 各人晚的量也不同 → 根本不在同一拍上。
现在消息里带主机的发出时刻，收到方减掉传输时间。主机自己也等满 `DelayMs` 再开始。

**五、变速也要定一个全场统一的生效时刻。** 与第四条同源。
各机"收到就立刻切"会在切换窗口里跑出不同速度，留下一个"往返延迟 × 新速度"的固定位置差
（实测 374 毫秒）。现在命令里带延迟，各机在本机等到同一个时刻再切。

这里还有一个更细的点：**冻结值必须按旧速度算到切换时刻**，不能停在"排定这一刻的位置"。
排定这一刻各机不同（主机是发出时刻，成员是收到时刻，差半个往返），
停在各机自己的当前位置就会把这个差原样变成位置差（实测 187 毫秒）。
改成"旧速度走到统一切换时刻"的值之后，各机算出来的是同一个数，位置差为 0。

**六、稳态播放不要每份快照都重设锚点。** 主机的快照每 5 秒无条件来一份。
每份都拿来重设锚点，就等于每 5 秒把"这条消息在路上花掉的时间"当成一次后退
塞进播放位置：实测位置推进速度掉到 0.87 倍。
现在只有"刚开演 / 本机没有锚点 / 差得超过 0.35 秒"才重设，稳态只信本机单调锚点。

另外两个顺手修掉的：

- **成员上报就绪前，自己的那一行可能还不在成员表里**（要等主机第一份快照回来）。
  原来去镜像里找自己会找不到，改动被静默丢掉，上报永远是"未就绪"，主机永远等不到全员就绪。
  现在就绪、声部、移调都存在本机字段里，不靠镜像。
- **改速度时先改 `_speed` 再重设锚点**，会让 `PositionNow()` 把"速度变化到现在这段时间"
  按新速度重算一遍，变速瞬间进度跳一下。现在先按旧速度重设锚点，再改速度。

### 19.3 一个设计上的认识

**不要比较两台机器的时钟，连"差不多"都不要。** 位置只由本机单调时钟的锚点推算，
快照里的位置只在一个明确的事件（开演、跳转、迟到入场）上用来定时，
而且用完就丢。这条来自参考项目 Bili-SyncPlay 的教训，实测证明是对的：
公开代理下往返 700 毫秒、抖动却只有 1 毫秒，位置差仍然稳定在 0 毫秒。

### 19.4 一个裁剪相关的坑

单文件裁剪版里 `JsonSerializer` 默认**禁用基于反射的序列化**，
直接抛 `Reflection-based serialization has been disabled for this application`。
所以远程同演的全部消息类型都必须登记在 `SyncJsonContext`（源生成器）里。
新增消息类型时忘了补一行 `[JsonSerializable]`，编译能过、运行时才炸。
