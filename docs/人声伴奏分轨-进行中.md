# 音频 → 人声 / 伴奏 两轨 MIDI：进行中的工作记录

写这份文件是为了让下一个会话（或下一个人）接着干，不用重新摸索。

## 目标

用户要的：音频进去，MIDI 出来，左边列表两条轨——一条「人声」，一条「伴奏」。
FuFumidi 的做法（已核对它的源码 `engine/engine_separate.py`）：用 demucs 先分离声部，
再对每个声部各自跑 basic-pitch，写出多音轨 MIDI。它**没有**「MIDI 转 MP3 后识别乐器」这种功能。

## 已定方案

- 分离模型：Spleeter 2-stem（FP16 ONNX，两个文件，各 18.8 MB）。
  来源：https://github.com/k2-fsa/sherpa-onnx/releases/tag/source-separation-models
  （`sherpa-onnx-spleeter-2stems-fp16.tar.bz2`，内含 `vocals.fp16.onnx` 与 `accompaniment.fp16.onnx`）
  选它的理由：正好两轨（人声 / 伴奏）、CPU 上很快（官方数据 RTF ≈ 0.07）、ONNX 体积小。
  UVR MDX-Net 是 28 MB 单模型但慢十倍；htdemucs ONNX 是 158–316 MB，太大。
- 模型不进 exe：exe 体积必须守住（当前基线 23 MB）。改成本机首次使用时下载到
  `%LOCALAPPDATA%\MidiKeyPlayer\`，用现有 `Engine\AutoUpdate.cs` 的网络能力。
- 推理：不引 ONNX Runtime，扩展仓库自写的极简执行器 `Audio\Onnx\OnnxGraphRunner.cs`。

## 模型口径（从 sherpa-onnx 的 C++ 实现逐行核对）

参考：`sherpa-onnx/csrc/offline-source-separation-spleeter-impl.h`

1. 音频：44.1 kHz、立体声。左右声道各自做 STFT。
2. STFT：参数写在模型元数据里（`n_fft` / `hop_length` / `window_length` / `window_type` / `center`）。
   实测该模型元数据里**没有**这几项，只有 `sample_rate=41000`（明显是笔误）、`stems=2`、`model_type=spleeter`。
   所以按 Spleeter 官方默认取：`n_fft=4096`、`hop_length=1024`、`win_length=4096`、Hann 窗、center=true。
3. 入口张量：`[2 声道, 帧数/512, 512, 1024]`，数据是**幅度谱**（`sqrt(real² + imag²)`），
   帧数先补齐到 512 的整数倍（不足就补零）。排布：先左声道全部帧，再右声道全部帧；
   时间轴按 512 一 chunk，频点 1024。
4. 出口张量：与入口同形状，是**幅度估计**，不是掩码。
5. 掩码（在 sherpa 里做，不在模型里）：
   `sum = vocals² + accomp² + 1e-10`，`maskVocals = (vocals² + 1e-10/2) / sum`，
   `maskAccomp = (accomp² + 1e-10/2) / sum`，再把掩码乘回原复数谱，最后 iSTFT。
6. 内存：整首歌一次性喂进去会爆（3 分钟约 22 MB 音频 → 入口张量几 GB）。
   要按 512 帧一块分块推理（每块约 11.9 秒音频，入口约 4 MB），块与块之间共享 chunk 边界帧。

## 已完成

`MidiKeyPlayer/Audio/Onnx/` 的执行器扩到了能跑这个图：

- 新增算子：`ConvTranspose`（权重 `[C_in, C_out/group, kH, kW]`）、`BatchNormalization`、
  `LeakyRelu`、`Identity`、`Constant`（含 `value` 张量与 `value_ints` / `value_floats`）、`ConstantOfShape`。
- `Constant` 的 `value` 是 TensorProto 属性：读属性时要按偏移切原始字节，之前只支持标量属性，已修。
- 标量张量（shape 为空）的元素数是 1 而不是 0：`OnnxTensor.ElementCount` 与 `OnnxModel.BuildTensor` 都修了。
- fp16 / bf16 权重解码成 float32（`FromHalf` / `FromBFloat16`）。模型就是 fp16 量化的，
  不解码会得到「有形状没数据」的张量，后面所有算子都吃空指针。
- `Cast` 目标类型是 fp16（编号 10）时按 float32 处理；`to` 属性被读成 int / long[] 两种都认。
- `Slice`：ONNX 的哨兵值 `INT64_MIN/INT64_MAX` 必须**先**夹到合法范围再算个数，
  直接 `Math.Clamp` 会往错的方向夹。这套口径用 onnxruntime 逐条比对过
  （脚本：`E:\APP\deepseek工作区\.dsh-scratch\slice_check.py`，5 个用例全对，
  含 `axes=[0] starts=[-1] ends=[INT64_MIN] steps=[-1]` 这种反向切片）。
- `Pad`：pads 长度支持 2*rank / rank / 1 三种口径；输出张量跟着输入的实际数据（F 还是 L）分配，
  不再只看声明类型。
- 图的节点顺序不保证依赖在前（TF 导出的图会乱）：`OnnxGraphRunner` 改成按需回溯
  （`Materialize` + 产出者表），不再按数组顺序硬跑。
- `Conv`：**当前按 NCHW 处理**（输入 `[N,C,H,W]`、权重 `[M,C/g,kH,kW]`）。
  注意 basic-pitch 的图是 NHWC 口径（权重 `[kH,kW,C,M]`），两种口径需要在同一个执行器里共存，
  下一个会话要按权重形状自动判定 —— 这一步**还没做**。

## 卡在哪

用 `MIDIKEY_SPLEETER_PROBE` 探针喂 `[2,1,512,1024]`（图里没声明入口形状，这是已知口径）
跑到最后卡在 `Concat`：

```
输入 /conv4/Conv_output_0[1,256,13,29] /bn5/BatchNormalization_output_0[1,256,10,26]
```

两个分支的空间尺寸对不上（13×29 对 10×26），差 3。含义：**空间轴的口径还没对**。
可能的方向（按可信度排）：

1. 入口张量的时间轴与频点轴写反了：试 `[2,1,1024,512]`。
2. 模型的 nn 图把 `(时间, 频点)` 当 `(H, W)`，而 U-Net 的 skip 在某一层需要 padding 才能对齐
   （Spleeter 原版在 TF 里用 `same` padding；ONNX 导出后靠显式 `Pad` 节点补，我的 `Pad` 口径可能还差一处）。
3. `ConvTranspose` 的 `output_padding` / `pads` 口径不一致。

定位手段已经就绪：`runner.Trace` 会把每个算子的输出形状打出来（`SpleeterProbe` 已挂上），
拿 onnxruntime 跑同一份输入输出逐层形状对比最快（Python 3.11 + onnxruntime 1.20.1 已装好）。
