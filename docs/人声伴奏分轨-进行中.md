# 音频 → 人声 / 伴奏 两轨 MIDI：进行中的工作记录

写这份文件是为了让下一个会话（或下一个人）接着干，不用重新摸索。

## 目标

用户要的：音频进去，MIDI 出来，左边列表两条轨——一条「人声」，一条「伴奏」。
FuFumidi 的做法（已核对它的源码 `engine/engine_separate.py`）：用 demucs 先分离声部，
再对每个声部各自跑 basic-pitch，写出多音轨 MIDI。它**没有**「MIDI 转 MP3 后识别乐器」这种功能。

## 已定方案

- 分离模型：Spleeter 2-stem（FP16 ONNX，两个文件，各 18.8 MB）。
  来源：https://github.com/k2-fsa/sherpa-onnx/releases/tag/source-separation-models
  （`sherpa-onnx-spleeter-2stems-fp16.tar.bz2`，内含 `vocals.fp16.onnx` 与 `accompaniment.fp16.onnx`）
  选它的理由：正好两轨（人声 / 伴奏）、CPU 上很快（官方数据 RTF ≈ 0.07）、ONNX 体积小。
  UVR MDX-Net 是 28 MB 单模型但慢十倍；htdemucs ONNX 是 158–316 MB，太大。
- 模型不进 exe：exe 体积必须守住（当前基线 23 MB）。改成本机首次使用时下载到
  `%LOCALAPPDATA%\MidiKeyPlayer\`，用现有 `Engine\AutoUpdate.cs` 的网络能力。
- 推理：不引 ONNX Runtime，扩展仓库自写的极简执行器 `Audio\Onnx\OnnxGraphRunner.cs`。

## 模型口径（从 sherpa-onnx 的 C++ 实现逐行核对）

参考：`sherpa-onnx/csrc/offline-source-separation-spleeter-impl.h`

1. 音频：44.1 kHz、立体声。左右声道各自做 STFT。
2. STFT：参数写在模型元数据里（`n_fft` / `hop_length` / `window_length` / `window_type` / `center`）。
   实测该模型元数据里**没有**这几项，只有 `sample_rate=41000`（明显是笔误）、`stems=2`、`model_type=spleeter`。
   所以按 Spleeter 官方默认取：`n_fft=4096`、`hop_length=1024`、`win_length=4096`、Hann 窗、center=true。
3. 入口张量：`[2 声道, 帧数/512, 512, 1024]`，数据是**幅度谱**（`sqrt(real² + imag²)`），
   帧数先补齐到 512 的整数倍（不足就补零）。排布：先左声道全部帧，再右声道全部帧；
   时间轴按 512 一 chunk，频点 1024。
4. 出口张量：与入口同形状，是**幅度估计**，不是掩码。
5. 掩码（在 sherpa 里做，不在模型里）：
   `sum = vocals² + accomp² + 1e-10`，`maskVocals = (vocals² + 1e-10/2) / sum`，
   `maskAccomp = (accomp² + 1e-10/2) / sum`，再把掩码乘回原复数谱，最后 iSTFT。
6. 内存：整首歌一次性喂进去会爆（3 分钟约 22 MB 音频 → 入口张量几 GB）。
   要按 512 帧一块分块推理（每块约 11.9 秒音频，入口约 4 MB），块与块之间共享 chunk 边界帧。

## 已完成

`MidiKeyPlayer/Audio/Onnx/` 的执行器扩到了能跑这个图：

- 新增算子：`ConvTranspose`（权重 `[C_in, C_out/group, kH, kW]`）、`BatchNormalization`、
  `LeakyRelu`、`Identity`、`Constant`（含 `value` 张量与 `value_ints` / `value_floats`）、`ConstantOfShape`。
- `Constant` 的 `value` 是 TensorProto 属性：读属性时要按偏移切原始字节，之前只支持标量属性，已修。
- 标量张量（shape 为空）的元素数是 1 而不是 0：`OnnxTensor.ElementCount` 与 `OnnxModel.BuildTensor` 都修了。
- fp16 / bf16 权重解码成 float32（`FromHalf` / `FromBFloat16`）。模型就是 fp16 量化的，
  不解码会得到「有形状没数据」的张量，后面所有算子都吃空指针。
- `Cast` 目标类型是 fp16（编号 10）时按 float32 处理；`to` 属性被读成 int / long[] 两种都认。
- `Slice`：ONNX 的哨兵值 `INT64_MIN/INT64_MAX` 必须**先**夹到合法范围再算个数，
  直接 `Math.Clamp` 会往错的方向夹。这套口径用 onnxruntime 逐条比对过
  （脚本：`E:\APP\deepseek工作区\.dsh-scratch\slice_check.py`，5 个用例全对，
  含 `axes=[0] starts=[-1] ends=[INT64_MIN] steps=[-1]` 这种反向切片）。
- `Pad`：pads 长度支持 2*rank / rank / 1 三种口径；输出张量跟着输入的实际数据（F 还是 L）分配，
  不再只看声明类型。
- 图的节点顺序不保证依赖在前（TF 导出的图会乱）：`OnnxGraphRunner` 改成按需回溯
  （`Materialize` + 产出者表），不再按数组顺序硬跑。
- `Conv`：已改成 **NCHW**（输入 `[N,C,H,W]`、权重 `[M,C/g,kH,kW]`）—— 这是 ONNX 规范口径，
  Spleeter 就是这个口径。改完 basic-pitch 那条路仍然正常（自检里的和弦识别用例通过）。
  但 basic-pitch 的导出器用的是哪种口径要在下个会话确认一次：如果它是 NHWC，
  执行器需要按权重形状自动判定（例：权重第二维等于输入第二维 → NCHW，否则 NHWC）。

## 卡在哪（第 3 轮更新）

**已定位到范围**：批归一（BatchNormalization）本身没有问题，问题在「整图跑」的时候：

| 检查 | 结果 |
|---|---|
| 单独算 bn（用模型里真实的 bn 参数、真实输入） | 与参考一致（头 4 个逐位相同，均值相同） |
| 单算子 Conv / ConvTranspose / Slice / fp16 解码 | 与 onnxruntime 一致 |
| 整图跑完后，出口与参考比 | 不一致（掩码几乎恒为 1，参考接近 0） |

所以嫌疑集中在**整图运行时的状态管理**：某个张量的数据被后续算子改写，
或者某个中间张量在 3 维/4 维时索引算错（单算子测试只覆盖了 4 维）。

下一步最值得做的两件事：

1. 把执行器的张量改成**不可变**：任何算子都必须写新数组，绝不原地改写
   （`OnnxTensor.WithDims` 会共享数据，`Pad`/`Slice`/`Concat`/`Unsqueeze` 的输出与输入共享底层数组，
   这是最可能的错源）。改完再跑一次全图比对。
2. 如果还不对，就把 `Spleeter` 的 U-Net 换成**直接用现成 ONNX Runtime**（NuGet）跑一遍对照，
   确认是模型口径还是执行器的问题。代价：exe 会从 23 MB 涨到 35 MB 以上，与「精致小巧」冲突，
   不到万不得已不走。

可复现的脚手架（都在 `E:\APP\deepseek工作区\.dsh-scratch\`）：

- `gen_ref.py`：生成固定输入 `ref_input.f32` 与 onnxruntime 参考输出 `ref_output.f32`
- `probe_all.py`：把中间张量加成图输出，拿可信的中间值（**推荐**，见下方注意）
- `slice_check.py` / `conv_ref.py` / `layer_ref.py`：单算子核对
- `truncate_model.py`：按中间张量截断建子图（本模型的节点顺序不是拓扑序，截断会失败，留着做参考）

注意：**不要用按名字打点的方式看中间值**。图里后面的算子会原地改写同一块内存，
打出来的是最终输出，不是那一层的值（本项目为此误判过两层算子）。
只有「把那个张量加成图输出、整模型跑一次」拿到的值才可信。

探针环境变量：`MIDIKEY_SPLEETER_PROBE`（模型目录）、`_ONLY=vocals`、`_IN`/`_REF`（固定输入与参考输出）、
`_DUMP=<张量名>`、`_CT=<前缀>`（单算子）、`_FP16=<前缀>`（fp16 解码）、`_BN=<前缀>`（批归一）、
`_SERIAL=1`（强制串行）。

模型的**形状已经全部对上**：入口 `[2, 声道数?, 512, 1024]`（外部喂 `[2,1,512,1024]` 会被图里的
Transpose 变成 `[1,2,512,1024]`），出口 `[2,2,512,1024]`。整图能在 4 秒左右跑完一遍。

数值上目前的状态：**逐算子都对，整图对不上**。逐算子核对的结果：

| 检查项 | 结果 |
|---|---|
| `Conv`（含步长 2、SAME 填充、dilation=2 三种） | 与 onnxruntime 逐元素一致（差 < 1e-7） |
| `ConvTranspose`（步长 2、填充 0/1） | 与 onnxruntime 逐元素一致（差 < 1e-7） |
| `Slice`（9 组用例，含反向切片与 INT64 哨兵值） | 与 onnxruntime 一致 |
| fp16 权重解码（12800 个数） | 与 numpy 逐位一致 |
| `Conv + BatchNormalization` 两节点子图 | 与 onnxruntime 一致 |
| 全模型最终输出 `y` | **不一致**（本实现掩码几乎恒为 1，参考接近 0） |

已修掉的真实缺陷（本轮）：

1. `Slice` 反向切片（负步长）的个数算多了一个：ONNX 用 `INT64_MIN` 当「切到头」的哨兵，
   终点要夹到 `[-1, dim-1]` 后**原样用负数**算个数。修之前 `starts=[-1] steps=[-1]`
   在长度 4 上取 5 个，越界。9 组用例现已与 onnxruntime 全对。
2. fp16 / bf16 权重解码（分离模型的权重就是 fp16）。
3. `Cast` 到 fp16（编号 10）按 float32 处理；`to` 属性被读成 int / long[] 两种都认。
4. `Constant` 的 `value` 是 TensorProto 属性，要按偏移切原始字节。
5. 标量张量（shape 为空）元素数是 1 而不是 0。
6. 算子属性里浮点值一律走 `OnnxNode.Float()`（float / double / 整型包装都认）。
7. 执行器改成按需回溯取值：TF 导出的图节点顺序不保证依赖在前。

未排查到底的方向：

- `BatchNormalization` 的通道索引（单算子子图对过，但全图里第二层起就对不上）。
- `LeakyRelu` 的 alpha（模型里可能不是默认 0.01）。
- `ConvTranspose` 在全图里的权重轴序（单算子对过，但只测了 3×3 与 5×5 两种）。
- 整图的某个 `Reshape` / `Transpose` 在 4 维以上时的轴处理。

关键矛盾的经验：**诊断打点的数值不可信**。`DumpValues` 拿到的是张量引用，
图里后面的算子会原地改写同一块内存，所以「按名字打点」打出来的经常是最终输出，
不是那一层的值。已改成快照复制，但下结论只认一件事：**把子图的输出当成图输出，跑一遍比最终数值**。

下一步定位手段（唯一可信的一条）：逐段截断模型，把每一段的输出加成图输出，跑一次比对：
把 `/conv/Conv_output_0`、`/bn/BatchNormalization_output_0`、`/conv1/Conv_output_0` ……
逐个当最终输出跑。哪一段开始数值偏了，问题就在那一段。
